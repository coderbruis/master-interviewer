# 资料与知识点建模

## 目标

把不同来源的材料转换成可提问、可评分、可复习的原子知识点目录，同时避免保存原始敏感内容。

## 支持的来源

- 简历：项目主张、职责、技术选型和量化结果。
- JD：岗位必备能力、加分项和业务场景。
- 项目或设计文档：架构、约束、决策、故障与验证方式。
- 技术文档或学习笔记：概念、机制、步骤、边界和实践。
- 代码：实际依赖、实现模式、测试和潜在风险。
- 历史问答：已覆盖主题、错误类型和复习优先级。

## 原子化规则

一个知识点应能被一道主问题独立检验。标题使用能力或机制名称，不直接复制长段原文。

不合格：

- `数据库、缓存和消息队列`
- `完整介绍项目架构、难点、性能优化和故障处理`

合格：

- `数据库范围锁`
- `缓存失效时序`
- `消息重复消费的幂等处理`
- `性能指标的测量口径`

需要同时回答两个互不依赖的问题时，应拆成两个知识点。追问可以验证同一知识点的更深层次，但不能借追问偷偷切换主题。

## 目录字段

目录是 JSON 数组，每项至少包含：

```json
{
  "topic_id": "database-range-lock",
  "label": "数据库范围锁",
  "kind": "document",
  "domain": "database",
  "project": "",
  "source": "technical-note:transactions"
}
```

- `topic_id`：稳定、小写、用连字符分隔；知识点未变化时不要改 ID。
- `label`：简短、可公开的能力名称。
- `kind`：来源类别，例如 `resume`、`document`、`jd` 或 `code`。
- `domain`：用于汇总的上级领域。
- `project`：安全的项目代称；非项目知识可使用空字符串。
- `source`：只保存来源类型和安全定位，不保存正文。

当前脚本要求以上六个字段。知识点优先级由面试流程结合材料重要性、覆盖情况和历史成绩判断，不写入个人原文。

## 隐私最小化

不要在目录或学习状态中保存：

- 原始简历、文档正文或大段代码。
- 电话、邮箱、身份证件、住址等身份信息。
- 客户名称、内部域名、访问令牌或未公开业务数据。
- 为出题不需要的公司、同事或供应商名称。

若来源定位本身敏感，改用抽象位置，例如 `project-doc:architecture-section`。
